# 双智能体交接与运行

## 调度和版本

1. 协调者读取本文件，确定稿件入口、用户授权和审查范围，准备含稿件所需文件的工作目录。LaTeX 输入目录只保留源文件和编译所需资源。脚本跳过 Git 元数据，稿件引用的链接资源应事先准备成普通文件。编译或渲染在版本目录之外写产物。
2. 使用宿主的真实子智能体工具。Codex 创建命名子智能体，后续轮次继续给原智能体派任务。DeepSeek Harness 选择支持后续消息的本地 `subagent`，用 `send_message` 给原 `reviewer` 和 `reviser` 派后续任务，等待完成通知，必要时用 `wait_agent`。如果没有支持继续派任务的子智能体工具，告知用户本次缺少双智能体执行能力。用户限定为单次审稿时仍可按指定范围审查。
3. Linux、macOS 或 Windows 都可用 Node.js 运行技能目录下的 `scripts/workflow.mjs`。下列命令中的脚本、运行目录和稿件用实际路径替换。运行目录必须是工作区内的新目录，且在稿件源目录之外。原始单文件直接传文件路径。LaTeX 多文件工程传目录，并用 `--entry` 给出相对主文件路径。

   ```text
   node "<脚本>" start "<运行目录>" "<稿件路径>" [--entry main.tex]
   node "<脚本>" status "<运行目录>"
   node "<脚本>" review "<运行目录>" <轮次> <pass|revise|needs-author|not-applicable>
   node "<脚本>" revision "<运行目录>" <轮次> <revised|no-progress|needs-author>
   ```

4. 只让协调者调用状态命令。按返回的 `phase`、`round` 和 `stage` 派任务，使用输出中的实际路径。完成后校验报告与稿件，接受这轮结果，根据新状态交给下一个角色。收到消息时核对角色、轮次和稿件路径，忽略过期回复。智能体未写齐文件时保留当前状态，先恢复这次交接。继续已有工作时先用 `status` 查询，沿用已接受的版本和问题编号。

## 固定四轮

| 轮次 | 审稿智能体 | 修订智能体 |
| --- | --- | --- |
| 1 · `academic-review` | 按[学术审查](academic-review.md)检查创新、论证、实验与证据，记录交给第二轮的技术线索。 | 落实本轮有证据且可直接修改的学术意见。 |
| 2 · `math-review` | 按[数学复核](math-review.md)独立复核公式、定理、假设和证明，给出推导、反例或核验缺口。 | 写入有依据且经作者确认的实质数学修订，逐项记录待确认内容。 |
| 3 · `english-editing` | 按[英文逐句编辑](edit-finalize.md#英文逐句编辑)定位需改的英文，给出原句、改句和理由。 | 逐句落实语言修改，保留原有技术含义。 |
| 4 · `final-review` | 按[全文终审](edit-finalize.md#全文终审)检查稿件及前三轮差异，复核问题是否关闭，给出终审结论。 | 交付以本轮核对过的稿件为准，遗留问题写入终审报告。 |

## 审稿交接

`phase=review` 时，把 `round`、`stage`、`manuscript` 和稿件目录、范围、目标期刊、需要的参考文件及指定的 `report` 路径交给 `reviewer`。第二轮起，加上前轮报告、已有的逐项回复和变更前稿件的位置。第四轮提供前三轮的全部报告和适用的逐项回复。请智能体完成后回报轮次、实际稿件路径、报告路径和审稿决定。

- 按上表完成当轮检查。第二、三轮同时核对前轮修订对本轮内容的影响。第四轮独立验证逐项回复、稿件差异和新增问题。沿用问题编号（如 `R01-001`），复发问题恢复原编号。
- `review.md` 写明稿件版本、覆盖范围、决定及逐项意见。每项包含编号、Critical/Major/Minor、定位锚点、证据和影响、建议及状态。有证据的错误、待核实事项和可选建议用不同状态标明。按实际复核结果关闭问题，修订智能体的自报只能作为线索。
- `pass` 表示本轮关键检查已完成、无需修改。`revise` 表示仍有可落实的必改项。`needs-author` 表示关键问题需要作者补材料或确认。第二轮无数学内容或第三轮无英文内容时，用 `not-applicable` 并记录原因。
- 协调者核对报告对应当前稿后执行 `review` 命令。前三轮的 `revise` 配合可编辑源稿会创建独立修订副本。其他情况保留当前稿，带着当轮报告进入下一轮。PDF 拟改项保留为定位意见，继续做后续可核查项目。

## 修订交接

`phase=revision` 时，把同轮的 `stage`、`manuscript`、`report`、`candidateManuscript` 及其目录、用户授权和指定的 `revisionLog` 路径交给 `reviser`。修订智能体先读整份审稿报告，再直接编辑候选稿及必要的源文件。完成后回报轮次、候选稿路径、回复路径和修订结果。

- 对有充分依据且在授权范围内的意见落实到稿件。保留引用键、公式标签、数学环境和文件结构。逐句编辑按[英文编辑](edit-finalize.md#英文逐句编辑)核对技术含义。涉及关键公式、定理、假设、数据或科学结论的实质改动，由作者逐项确认后写入稿件。缺数据、证明或确认时，给出具体拟改内容并保留问题状态。实验、引用、验证和数值按实际证据记录。
- 在 `changes.md` 逐项引用审稿编号，写明处理状态、修改位置、前后差异、核验情况及未落实的原因。新增文件或跨文件变更也要标明。打包、校验和生成比较文件优先在候选稿目录之外完成。
- `revised` 表示已落实修改。`no-progress` 表示没有可送审的新稿。`needs-author` 表示继续修订需要作者材料或确认。协调者核对候选稿变化和逐项回复后执行 `revision` 命令。接受 `revised` 后将新稿交回同一个 `reviewer` 进入下一轮。其他结果携带逐项回复，以当前稿继续下一轮。

## 停止与交付

第四轮结论应覆盖前三轮所有遗留问题。只有关键检查已完成且全部必改项均已关闭时才给出 `pass`。当 `phase=finished` 时，`passed` 表示通过终审，`open-issues` 表示仍有待改事项，`needs-author` 表示仍需作者处理。报告应指出剩余问题、影响和后续需要的源稿或证据。

用 `lastReviewedManuscript` 指向实际终审过的版本，用最后一条 `history` 的 `report` 指向终审结论，附各轮报告和逐项回复。LaTeX 交付稿件目录及主文件。若提前中断，分别标明最近已审稿与待审稿的状态。最终摘要说明四轮的核对结果、实际修订和剩余问题。
